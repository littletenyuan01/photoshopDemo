# GPU 加速开发计划（**可选加速后端**）

> 关联文档：[filter-roadmap.md](filter-roadmap.md)（滤镜现状与批次）、[engine/operators.md](engine/operators.md)
> （算子调用链）、[engine/roi.md](engine/roi.md)（请求区/输入区）、[dev-plan.md](dev-plan.md)（构建成本实测）。

---

## 0. 一句话

把 GPU 做成**可选的加速后端**：**有 GPU 就用它加速，没有就原样走 CPU**。
**不是**把 CPU 实现换成 GPU 实现 —— CPU 路径永远是基线、永远是降级路径、永远可跑。

---

## 1. 硬约束（后面的所有设计都不许违反）

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **CPU 路径永远存在且完整** | 它不是"旧代码"，是**正确性基准**（所有 oracle 测试的参照物）+ 降级路径 |
| 2 | **启动不许因为 GPU 失败而失败** | 探测不到、驱动缺失、显存不足 ⇒ 静默走 CPU |
| 3 | **逐次调用可降级** | 单次 GPU 提交失败（显存不够、kernel 编译失败）⇒ 这一次退回 CPU 重算，而不是报错 |
| 4 | **连续失败要熔断** | 失败 N 次后本次会话关闭 GPU，避免每次都白试一遍 |
| 5 | **结果必须与 CPU 一致（容差内）** | 现有 **24 个常驻用例就是 oracle**，GPU 路径必须过同一套（见 §7） |
| 6 | **不改 `.pslite` 格式、不改文档语义** | GPU 是实现细节，不该让文件变得"只有装了 GPU 才打得开" |
| 7 | **可强制开关** | 环境变量 / 设置项能强制 CPU 或 GPU，用于 A/B 对比与回归 |

> 第 1 条决定了架构：这是**策略模式（可插拔后端）**，不是**替换**。
> 所以第一步不是写 kernel，而是**把接口和调度做出来**（见 §5 的 P0）。

## 2. 现状（CPU 全包，代码位置）

| 层 | 现状 | 位置 |
|---|---|---|
| **瓦片存储** | `QHash<qint64, QImage> m_tiles`，64×64，**稀疏**（透明层 0 分配） | `domain/tilebuffer.{h,cpp}` |
| **投影** | 整文档一张 `QImage m_buffer` + 每 64×64 一块的 `QBitArray m_chunkValid`；`sync(maxMs)` **同步**语义（块数 + 时间双预算）；`const QImage &image()` 承诺"算完就在那儿" | `engine/projection.{h,cpp}` |
| **合成** | 逐图层、逐 64×64 块，CPU 逐像素混合；并行靠 `QThreadPool` 切行带 | `engine/compositor.{h,cpp}` |
| **滤镜链** | `FilterStack::apply` 把整条链依次作用在**同一张 QImage** 上 —— **纯函数** | `domain/filterstack.cpp` |
| **滤镜算子** | `FilterOp` 三段式（`prepare/process/finish`），**每线程一份**常驻实例 | `engine/op/*`、`engine/filtereval.cpp` |
| **绘制算子** | `BufferOp` 按瓦片写像素 | `engine/op/bufferop.h` + shapefill/gradient/… |
| **异步任务** | `LayerFilterJob` 用 `QtConcurrent` 按行带并行 | `engine/layerfilterjob.{h,cpp}` |

**关键观察**：`FilterStack::apply` 的输入输出都是**整块 QImage**，不碰瓦片、不碰文档、不读全局状态
—— 这是整个引擎里**最干净的接缝**（当初为了正确性这么设计，现在顺带成了 GPU 的入口）。

## 3. 目标架构

```
                 ┌─────────────── 调用方（不变）───────────────┐
   Layer::compositeRasterRegion / LayerFilterJob / 测试
                 └───────────────────┬─────────────────────────┘
                                     │  apply(stack, QImage)
                          ┌──────────▼──────────┐
                          │  FilterStack::apply │  ← 唯一改动的接缝
                          └──────────┬──────────┘
                                     │
                    ┌────────────────▼─────────────────┐
                    │        后端调度（新）            │
                    │  ① 探测可用性                    │
                    │  ② 按「链成本」决策 GPU / CPU     │
                    │  ③ 失败降级 + 熔断               │
                    └───────┬───────────────┬──────────┘
                            │               │
                  ┌─────────▼──────┐  ┌─────▼──────────┐
                  │ CPU 后端（必须）│  │ GPU 后端（可选）│
                  │  = 现在的实现   │  │  上传→链→回读   │
                  └────────────────┘  └────────────────┘
```

**接口草案**（示意，P0 定稿）：

```cpp
/** 一个后端能做什么 + 成本模型。 */
class RasterBackend {
public:
    virtual ~RasterBackend() = default;
    virtual QString name() const = 0;              // "cpu" / "gpu:vulkan" …
    virtual bool isAvailable() const = 0;
    /** 把整条链作用在 image 上。失败返回 false ⇒ 调用方退回 CPU 重算。 */
    virtual bool applyStack(QImage &image, const FilterStack &stack,
                            const std::function<bool()> &shouldAbort) = 0;
};
```

**关键点**：接口**只认整块 QImage**。GPU 后端自己在内部做「上传 → 链式 kernel → 回读」，
并且**一条链只来回传一次**（链级批处理）。

## 4. 决策规则（本计划的核心，也最容易做错）

### 4.1 按「链」决策，**不按「算子」**

反面例子：链 = [亮度, 中值, 反相]，按算子决策会变成

```
亮度(CPU) → 上传 → 中值(GPU) → 回读 → 反相(CPU)
   ↑ 两次往返 = 2 × 0.8 ns/px，白白多付一次
```

正确做法：**既然要传，就把整条链都放上去**（亮度/反相在 GPU 上本来就近乎免费）。

```
上传 → 亮度 → 中值 → 反相 → 回读
   ↑ 一次往返
```

### 4.2 判据：**链的每像素总成本 vs 一次往返**

一次往返的实测/估算成本（8.7 Mpx ≈ 35 MB，PCIe ~10 GB/s）：

```
往返 ≈ 7 ms ≈ 0.8 ns/px        （像素数在两边都成比例，所以基本会约掉）
```

于是判据化简成一个**链的静态属性**：

```
Σ(每个启用节点的 ns/px) > 阈值（初值 5 ns/px）  ⇒  整链走 GPU
```

**这是个很好的性质**：不需要在运行时猜像素数、不需要动态测量 —— 只要一张**每算子的成本常量表**
（已经实测过，见下表），求和比一下就完了。

| 算子 | 实测 ns/px | 上表 |
|---|---|---|
| 中值 r≥3 | ~187 | ✅ |
| 最大值 / 最小值 | ~100 | ✅ |
| 添加杂色（高斯彩噪） | ~22 | ✅ |
| 高斯模糊 | ~20 | ✅ |
| 自定滤镜 3×3 | ~20 | ✅ |
| USM / 高通保留 | ~15 | ✅ |
| 运动模糊（距离大） | ~15 | ✅ |
| 方框模糊（半径小） | ~5 | ⚠️ 临界 |
| 位移 | ~1.5 | ❌ |
| 亮度/对比度/反相/阈值/色阶 | ~0.5–1 | ❌ |

> 表里只有「≥ 5 ns/px」的算子会把链推向 GPU；点算子**永远不单独触发** GPU，
> 但**会被一起带上 GPU**（因为整链决策）。

### 4.3 附加门槛

- **像素数下限**：区域太小（如缩略图 < 10 万像素）时，内核启动/同步的**固定开销**占比过高 ⇒ 直接用 CPU。
- **强制开关优先**：环境变量强制 CPU 时，上面所有判断都不执行。

## 5. 分期（每期结束 CPU 路径都必须仍然完整可用）

### P0 — 壳与调度（**不写 GPU**）★ 最关键的去风险步骤

| 做什么 |
|---|
| 定义后端接口（`engine/backend/rasterbackend.h`） |
| 写 **CPU 后端**：内容就是现在 `FilterStack::apply` 的逻辑，原样搬过去 |
| 写调度器：能力探测 / 链成本决策 / 降级 / 熔断 / 强制开关 |
| `FilterStack::apply` 改成「问调度器要后端」，默认永远是 CPU |
| 加成本常量表（§4.2）+ 一个 `estimatedCostNsPerPixel()` |

**验收标准**
1. **全部 24 个用例保持绿**（此时后端只有 CPU，行为必须逐像素不变）；
2. 强制开关生效：设 `PSLITE_RASTER=cpu` / `=gpu` 能观察决策日志；
3. 熔断可注入测试：给一个「总是失败」的假后端，验证**每次调用都退回 CPU 重算且结果正确**，
   且失败 3 次后不再尝试。

**为什么先做这个**：接口形状、决策规则、降级路径**全部与有没有 GPU 无关**，
但它们是整个方案里最容易出错的部分。**用 CPU 实现就能把它们全部验证完。**

**风险**：低。唯一的实质改动是把 `FilterStack::apply` 的实现挪个位置（行为不变，测试兜底）。

### P1 — 第一个 GPU 算子（**只做中值**）

| 做什么 |
|---|
| 选定图形 API（见 §6） |
| 实现 GPU 后端骨架：设备/队列初始化、上传、回读、缓冲池 |
| **只实现中值 r≥3** 的 kernel；链里出现别的算子就先退回 CPU（整链决策，不混跑） |

**验收标准**
1. 中值结果与 CPU 版在**容差内一致**（先定容差，见 §7）；
2. 端到端（含上传回读）**比 CPU 快 ≥ 3×**，否则记录结论并**暂停 P2**；
3. 无 GPU 的机器上，所有用例照旧绿（这是"可选"的底线）。

**风险**：中。GPU API 选型 + 缓冲池 + 传输开销都可能低于预期。
**这条"快不到 3× 就停"是硬门槛** —— 避免在收益不成立的方向上继续投入。

### P2 — 按成本表铺开

按 §4.2 的表从高到低：最大值/最小值 → 高斯 → 自定滤镜 → USM/高通 → 运动模糊 → 添加杂色。

**注意两件事**
1. **排序统计类（中值/极值）在 GPU 上要换算法**（现在的"滑窗直方图 + 增量 cum"沿行**串行**，
   是 CPU 算法的形状）。GPU 上要么每像素排序网络（半径小），要么并行直方图 + 前缀和。
   **这不是移植，是重写。**
2. **位置相关算子（添加杂色）在 GPU 上反而更简单** —— 现在是"必须整层 CPU 求值"
   （`FilterStack::hasPositionalOp`），GPU 上纯散列无状态，这个约束自然消失。

### P3 —（可选，另一个量级）绘制算子

只做**最重的几个绘制操作**的特例：GPU 离屏渲染成一张普通 QImage，再按现在的方式塞回瓦片。
**绕开**投影/合成的执行模型。见 §8「不做的事」里的说明。

## 6. API 选型（**需要单独的 spike，P0 不依赖它**）

| 候选 | 优点 | 顾虑 |
|---|---|---|
| **Qt RHI（QRhi）** | Qt 6 内置，已抽象 Vulkan/D3D11/D3D12/Metal/OpenGL；与现有 Qt 工程无缝 | 为**渲染**设计，通用计算（compute shader）支持面窄，需要验证 |
| **OpenCL** | 通用计算成熟；与 OpenGL 互操作好 | Qt 6 不内置，要引入依赖（MinGW 下更麻烦） |
| Vulkan / D3D12 compute | 性能与可控性最好 | 代码量最大，平台分支多 |
| CUDA / HIP | 生态最好 | 平台绑定，与"可选、跨平台"的定位冲突 |

**建议路径**：spike 阶段**并行验证 QRhi compute 与 OpenCL 各写一个中值 kernel**，
用 P1 的验收标准（≥3×）挑一个。**P0 不需要等这个结论。**

## 7. 测试策略（"可选"能否成立的唯一保障）

| 层 | 做法 |
|---|---|
| **CPU 回归** | 24 个用例**默认全跑 CPU**；CI/无 GPU 机器必须全绿 |
| **一致性** | GPU 路径与 CPU 路径对同一输入比像素，**容差先定**（建议：逐通道允许 ±1，且不允许结构性差异）；先只在有 GPU 的机器上跑 |
| **降级** | 注入「总是失败」的假后端 → 验证每次退回 CPU 且结果正确、熔断生效 |
| **开关** | `PSLITE_RASTER=cpu|gpu|auto`，用于 A/B 与强制复现 |
| **性能** | 沿用一次性验证程序的做法（`.build-verify/*.cpp`），记录端到端（含传输）而不是只记 kernel 时间 |

> **一条纪律**：GPU 的收益**必须报"端到端含传输"的数字**。
> 只报 kernel 时间会得出错误结论 —— 本项目已经吃过两次"没量就改"的亏
> （预览降采样的 1/2 是白干、Box-Muller 比 Irwin–Hall 慢 20 倍）。

## 8. 不做的事（明确记录，避免范围蔓延）

| 不做 | 理由 |
|---|---|
| **不做「用 GPU 替换 CPU」** | 违反硬约束 1。GPU 永远是可选的加速器 |
| **不改 `.pslite` 格式 / 文档语义** | 硬约束 6。GPU 是运行时实现细节 |
| **P0–P2 不动瓦片 / 投影 / 合成** | 那是 15–20 个文件、4 个核心重写的量级（`tilebuffer` / `projection` / `compositor` / `bufferop`）。**"重滤镜加速"不需要付这个代价** |
| **不把点算子单独送 GPU** | 传输（~0.8 ns/px）会吃掉收益（点算子只要 ~1 ns/px） |
| **不追求 bit-exact** | 浮点/并行归约的顺序差异不可避免。定容差，而不是强求逐位相等 |
| **不引入平台绑定** | 与"可选、跨平台、无 GPU 也能跑"的定位冲突 |

---

## 9. 优先级与决策点

| 阶段 | 前置 | 决策点 |
|---|---|---|
| **P0** | 无 | 做完即有价值（接口 + 降级 + 开关全部可测），**建议立刻做** |
| **P1** | P0 + API 选型 spike | **≥3× 才继续**；否则记录结论并停在 P0 |
| **P2** | P1 达标 | 按成本表逐算子推进，每个算子单独验收 |
| **P3** | 另行评估 | 只有"拖动/绘制也要快"成为真实需求时才启动 |

**最后一条判断**：如果目标只是「**重滤镜别卡**」，**P0 + P1 就够了**。
P3（瓦片/合成上 GPU）是**独立的大工程**，`docs/engine/` 下要单开文档，不在本计划范围内。

# ROI（请求区 / 所需输入区）—— 为什么滤镜绕不开它

> 本文解释本项目滤镜引擎里那个贯穿一切的概念：**ROI**。
> 它是「按块合成 + 算子要读邻居」这两件事碰在一起的必然产物，也是「小块脏区只重算一点点」能成立的前提。
> 对照页：[operators.md](operators.md)（算子调度）、[../pending-dev.md](../pending-dev.md)（ROI 通用化的迁移设计）。

## 1. 一句话

> **ROI 通用化 = 让算子能回答「要算这块输出，我需要输入里的哪一块」，而且那块可以是任意矩形。**

现在本项目的算子只能回答「以请求区为中心、**对称**向外扩 p 圈」这一种形状；
GEGL/GIMP 里对应 `get_required_for_output()`，它返回一个**通用矩形**。

术语对照：

| 说法 | 含义 |
|---|---|
| **请求区**（out / want / ROI） | 这次要算出来的那块输出（典型是 64×64 的合成块，或画布可见区） |
| **所需输入区**（src / required input） | 为了算出请求区，必须准备好输入数据的那块 |
| 反向传播（back-propagation） | 从请求区推出所需输入区的过程 |

## 2. 为什么滤镜会牵扯到 ROI

因为**合成是分块的**（64×64），而滤镜**要读邻居**。两者一碰，就必须回答「算这一块，得喂哪一块」。

具体看**每个输出像素从哪里读输入**，算子分三类：

| 算子类型 | 输出像素读哪里 | 需要的输入 | 本项目现状 |
|---|---|---|---|
| **点算子**（亮度/对比度、反相） | 同一位置 `out(x,y) = f(in(x,y))` | 就是它自己 → pad = 0 | ✅ 天然没这个问题 |
| **邻域算子**（模糊、中值、3×3 锐化/浮雕/查找边缘） | 附近 `out(x,y) = f(in(x±r, y±r))` | 请求区**对称外扩 r 圈** | ✅ `inputPad()` 正好表达 |
| **几何算子**（位移、旋转、极坐标） | **别处** `out(x,y) = in(x-dx, y-dy)` | 一块**平移过的矩形** | ❌ 对称外扩表达不了 |

```
请求输出区 want（64×64）                邻域算子：要的是「外扩 r 圈」
┌────────┐                                    ┌──────────────┐
│  want  │  ← 算它，需要邻居                 │   srcWant    │
└────────┘                                    │  ┌────────┐  │
                                              │  │  want  │  │   ← 对称，好用 ✓
几何算子（位移 dx,dy）：要的是「平移过去的那块」│  └────────┘  │
        ┌──────────────┐                      └──────────────┘
        │   srcWant    │
        │      ┌───────┴──┐
        └──────┤  want    │                  ← 同样大小，但**偏在一边**：对称机制表达不了 ✗
               └──────────┘
```

### 为什么不能干脆「整层重算」

那就是本项目踩过的坑：64×64 的笔触却触发整层重算，实测 **447 ms** 卡顿。
ROI 反向传播就是让「小块脏区」只重算必要输入的那套机制，把 447 ms 压到 **8.9 ms**。
所以 ROI 不是滤镜的附加负担，而是**分块缓存能成立的前提**。

### 为什么答错会出可见 bug

所需输入区不够 → 64×64 块边界处邻居缺失 → 画面上出现**网格状接缝**。
这正是每个面积算子的「**分块投影 == 整幅合成，diffs=0**」断言守的东西（见 [../tests.md](../tests.md) 的 `areafilter`）。

## 3. 现状机制：只能对称外扩

| 位置 | 代码 |
|---|---|
| 标量外扩 | `FilterNode::inputPad()` → `int` |
| 滤镜栈求和 | `FilterStack::totalPad()` |
| 像素层路径 | `Layer::compositeRasterRegion(want)`：`srcWant = want.adjusted(-pad,-pad,pad,pad) ∩ 层范围`，之后**按 pad 取中心裁回**；并把 `(srcWant, want)` 按文档坐标交给 `FilterStack::apply(source, srcRect, outRect, shouldAbort)` |
| 图路径 | `PointFilterOp::requiredInputs(out)` → `{ out.adjusted(-p,-p,p,p) }`（**输出仍与输入同尺寸**，不做裁回 —— 见 §5 的 ② 步骤） |
| 几何去向 | `FilterContext::srcRect / outRect`（**输入图本地坐标**；由 `PointFilterOp` 从文档坐标换算） |

## 4. 与 GIMP / GEGL 的对照

| | GIMP / GEGL | 本项目现状 |
|---|---|---|
| 输入需求的接口 | `get_required_for_output(operation, input_pad, output_roi) → **GeglRectangle**`（通用矩形） | `FilterNode::inputPad() → int`（对称标量） |
| 算子拿到什么 | `process` 里的 `roi` 是**输出矩形**，输入按需索取 | 拿到**整幅补边图**，就地处理 |
| 谁来裁剪 | 算子自己按映射写输出 | 调用方按 pad **取中心** |
| 每个节点的缓冲 | **每个节点各持一个 buffer**（请求式求值） | 一个滤镜栈共用一张补边图 |

参考实现：`gimp-master/app/operations/gimpoperationoffset.c` ——
`gimp_operation_offset_get_required_for_output()` 直接返回
`gimp_operation_offset_get_rect(offset, TRUE, output_roi, &rect)`，即**把输出矩形平移 (dx,dy)**。
（该算子还设了 `cache_policy = GEGL_CACHE_POLICY_NEVER`。）

用对称外扩去逼近位移的代价：`p = max(|dx|,|dy|)` ⇒ 每个 64×64 块要取 `(64+2p)²` 输入。
偏移 500px 时是 `(64+1000)² ≈ 113 万`像素，而真正需要的只有 `4096` —— **276 倍**无用功。
更麻烦的是 PS 默认的 **wrap-around**：它是**多矩形**依赖（区域在右边缘时要读最左边），单矩形机制无从表达。

## 5. 迁移设计（三步）—— **①② 已落地，③ 等「多矩形」的决策**

| 步骤 | 内容 | 验收标准 | 状态 |
|---|---|---|---|
| ① 契约带几何 | `FilterContext` 增 `QRect srcRect; QRect outRect;`（**文档坐标**）；两条路径填真值；`FilterEval::applyNode(image, node)` 直调路径保持「src = out = 图像自身」语义 | **七个面积算子行为完全不变 ⇒ 全套测试保持绿** | ✅ **已落地**（见下「① 落地说明」） |
| ② 裁剪按几何 | 输入需求改由**链自己声明**：`FilterNode::requiredInputs(output)` + `FilterStack::requiredInputRect(output)`（自栈顶倒推）；`compositeRasterRegion` 与 `LayerFilterJob` 都改用它；裁剪点 = `want.topLeft() - srcWant.topLeft()` | 测试仍绿，且**能表达不对称需求** | ✅ **已落地**（见下「② 落地说明」） |
| ③ 算子契约改 `process(const QImage &src, QImage &out, ctx)` | 算子从 ctx 读映射、自己写输出 | 破坏性：七处内环取样基准都要改 | ⏸ **未做**（理由见下，**已更新**） |

### ① 落地说明（实际做了什么、几何用哪个坐标系）

- `FilterContext` 新增 `srcRect` / `outRect`，**一律用「输入图本地坐标」**（输入图 `(0,0)` 为原点）；
- `FilterStack::apply(source, srcRect, outRect, shouldAbort)` 的入参用**文档坐标**（与
  `Layer::compositeRasterRegion` 里 want/srcWant 同一空间），由 `PointFilterOp` 负责
  减掉 `srcRect.topLeft()` 换算成本地坐标 —— 调用方不必关心坐标系；
- `Layer::compositeRasterRegion` 现在真的把「请求区 / 所需输入区」按文档坐标传下去；
- **七个面积算子一行未改**（它们本来就只依赖「手里这张图」与 `inputPad`），全套测试保持绿。

> 坐标系为什么选这一套：`srcRect` 只描述「手里这张图里，哪一块是合法的输出区」，
> 所以它必须是本地坐标；而调用方（像素层）手里只有文档坐标。把换算收在
> `PointFilterOp` 一处，比让每个调用方各算一遍更不容易错 —— 本轮实测就错了两次（见缺陷台账 #16/#17）。

### ② 落地说明（能表达不对称，并已变成可测的收益）

- `FilterNode::requiredInputs(const QRect &output)`（**层内坐标**）：想算出 output，输入至少要有哪一块。
  默认实现 = 对称外扩 `inputPad()`，与旧行为**逐像素一致**；运动模糊按角度返回不对称矩形
  （0° 只扩左右、90° 只扩上下、45° 两向都扩）；
- `FilterStack::requiredInputRect(output)`：**自栈顶往栈底倒推**。对称 pad 时倒推与逐项求和等价
  （所以与旧 `totalPad()` 行为一致）；**不对称时必须倒推**，求和会把两轴需求混着算多；
- `compositeRasterRegion` 与 `LayerFilterJob` 都改用 `requiredInputRect`；裁剪按几何
  （`want.topLeft() - srcWant.topLeft()`），不再假设 pad 对称；
- `LayerFilterJob` 的条带边界改成**按侧**的 `padLeft/Top/Right/Bottom`，且必须由**未裁剪**的需求
  得出：层边缘会把 `srcLocal` 裁掉，但条带仍需向外多取（靠 `∩ snap.rect()` 兜住）。

**实测收益**（1024×1024，按 64×64 块逐块「裁输入→求值→裁回」，完全模仿投影）：

| 场景 | 旧（对称 pad） | 新（链自声明） | 取样面积 |
|---|---|---|---|
| 运动模糊 0°，距离 64 | 160 ms | **39 ms（0.24×）** | 0.35× |
| 运动模糊 0°，距离 128 | 418 ms | **59 ms（0.14×）** | 0.22× |
| 运动模糊 45°，距离 64 | 256 ms | 219 ms（0.86×） | 1.00×（两向本就需要） |

### ③ 为什么仍然不做（**理由已随 ①② 与「移除环绕」而更新**）

原理由「②③ 与 offset 绑定后置」**已失效**：offset 最后走的是**逐块路径**
（`requiredInputs` 返回「输出区 ∪ 平移后的输出区」，单矩形），没走通用机制。
而**环绕位移已被彻底移除**（见 [../pending-dev.md](../pending-dev.md) 的「后续：环绕已彻底移除」）——
它曾是代码里**唯一**的多矩形依赖，所以「要不要支持多矩形」这个上游决策**自动消失了**。

现在 ③ 只剩一条理由与一条代价：

- **收益**：让算子不再计算「随后会被裁掉的边」。按 ② 之后的几何，投影每块 64×64、
  半径 r 时可省 `1 − 64/(64+2r)` —— r=3 时 ≈ 8.6%、r=8 时 ≈ 20%，量级 1.2–1.25×；
- **代价是破坏性的**：七个面积算子的内环取样基准全要改（`process(QImage&)` 变成
  `process(const QImage&, QImage&, ctx)`），一次性大 diff；正确性可以靠现有 oracle 用例守。

⇒ **结论：不值得单独做。** 除非将来出现「算子需要各自独立的中间缓冲」的真实需求
（那正是 GEGL 让每个节点各持一个 buffer 的原因），否则 ③ 只是纯技术债。

### 历史记录：多矩形曾经是什么（现已不存在）

在「环绕」还被保留时，它是唯一的**多矩形**依赖：要算输出最左边那几个像素，得去读输入的
**最右边**；要算最右边，又得读最左边。单矩形（`QRect` 是一块实心方块）表达不了
「我要最左一块 + 最右一块、中间不要」，于是只能退化成整层求值 —— 这就是当初
`hasGeometryOp()` 那条「整层专用路径」存在的唯一原因，也是它现在能整个删掉的原因。

### 历史记录：②③ 当初为什么后置（**保留原文，便于对照决策变化**）

当初把三步全做完的代价是 **12 个代码文件**（含 7 个已正确的面积算子内环）＋测试与文档；而收益只有一个
「以后几何算子能装进来」。更关键的是，按本文 §4 的结论，通用化之后：

- **wrap-around 仍装不下**：PS 默认的位移是**多矩形**依赖（右边缘读最左边），单矩形机制无从表达；
- 单矩形下 offset 若用对称外扩逼近，偏移 500px 时每个 64×64 块要取 ~113 万像素（276 倍无用功）——
  也就是说「只做 ①②③ 而不做多矩形」并不能让 offset 变得可用；
- 栈里仍只能有**一个几何算子且必须在最后**（下一条那条限制依旧）。

当年的决策是：**②③ 与「真的要做 offset」一起做**。事后看这个决策**只对了一半**：
offset 最终没有走通用机制（它走了整层专用路径），所以「绑定」没发生；而 ② 本身有独立价值
（不对称需求 → 运动模糊实测 0.14–0.31×），于是 ② 被单独捞出来做了（本轮）。
③ 仍未做，理由已更新为上面那一节。

### 多算子栈的额外门槛（别低估，也是 ③ 后置的理由之一）

栈里若含非 pad 类算子（如 offset），**每个算子都需要各自的中间缓冲与几何**，
不能像现在这样「所有滤镜依次作用在同一张补边图上」：

```
现状（共用几何）:  srcWant ──[模糊]──[USM]──[锐化]──► 裁回 want
含几何算子      :  srcWant ──[模糊]──► 中间图A ──[位移]──► 中间图B ──► 裁回 want
                                      ↑ 几何不同，得各持一个 buffer
```

这正是 GEGL 让**每个节点各持一个 buffer** 的根本原因。
⇒ 补第 ③ 步之前先决策：**是否接受「一个栈里最多一个几何类算子、且必须在最后」**这种受限语义
（可以先上 offset，代价是记一条明确限制）。

## 6. 已落地的一条相关实践

滤镜对话框的**区域化预览**（`ImageDocument::setLayerFilterNodePreview(..., region)`）就是 ROI 思想在 UI 上的应用：
只把**画布可见区**标脏，屏幕外的旧像素不动（对话框是模态的，视口不会变），因此拖动参数不会整层重算。
见 [../pending-dev.md](../pending-dev.md) 的「滤镜预览的两道护栏」。
